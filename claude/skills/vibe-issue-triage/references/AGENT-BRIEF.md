# Agent Brief Format

An Agent Brief is the structured comment posted on an issue when it moves to `ready-for-agent` (or `ready-for-human`). It is the **authoritative specification** that an AFK agent works from. The original issue body and discussion are context; the Agent Brief is the contract.

## Principles

### Durability over precision

The issue may sit in `ready-for-agent` for days or weeks. The codebase will change. Write the brief so it stays useful even as files are renamed, moved, or refactored.

- **Do** describe interfaces, types, behavioral contracts
- **Do** name specific types, function signatures, or config shapes the agent should look for
- **Don't** reference file paths — they go stale
- **Don't** reference line numbers
- **Don't** assume the current implementation structure remains the same

### Behavioral, not procedural

Describe **what** the system should do, not **how** to implement it. The agent will explore fresh and make its own implementation decisions.

- **Good**: "The `SkillConfig` type should accept an optional `schedule` field of type `CronExpression`"
- **Bad**: "Open `src/types/skill.ts` and add a schedule field on line 42"
- **Good**: "When a user runs `/triage` with no arguments, they should see a summary of issues needing attention"
- **Bad**: "Add a switch statement in the main handler function"

### Self-contained body — no thread reliance

The Agent Brief comment must contain everything the agent needs. Do **not** put requirements in earlier discussion comments and assume the agent will read them. Different platforms read comment threads differently:

- **Copilot Coding Agent** freezes the thread at assignment; later comments require an `@copilot` mention on the resulting PR
- **OpenHands resolver** aggregates comments but can drop them under context pressure
- **Aider** typically reads body only

The brief is the one artifact every agent reliably reads. Make it complete.

### Complete acceptance criteria

Every brief has concrete, testable acceptance criteria. Each criterion independently verifiable.

- **Good**: "Running `gh issue list --label needs-triage` returns issues that have been through initial classification"
- **Bad**: "Triage should work correctly"

### Verification (required for `ready-for-agent`, optional for `ready-for-human`)

For AFK issues, the brief must include **at least one executable check** the agent can run to verify the work is complete — a test command, a curl, a screenshot diff, a CI job. Prose acceptance criteria alone leak into "looks-correct-but-wrong" submissions; an executable check makes "done" falsifiable.

For HITL issues, this is optional — a human is judging the result.

### Repo policies in effect (load-bearing)

Inline (don't link) the policies from `CLAUDE.md` / `AGENTS.md` / `docs/agents/` that apply to this issue: "no new dependencies", "ask before schema migration", "secrets only via env", etc. Different agent platforms load CLAUDE.md inconsistently; the issue body is the only surface every agent reliably loads.

Two paragraphs at most. If a policy doesn't apply to this issue, leave it out — don't pad.

### Explicit scope boundaries

State what's **out of scope for this slice**. Prevents gold-plating. If there's nothing slice-specific to flag, omit the field.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen.

**Current behavior:**
What happens now. For bugs: the broken behavior. For enhancements: the status quo the feature builds on.

**Desired behavior:**
What should happen after the work is complete. Be specific about edge cases and error conditions.

**Key interfaces:**
- `TypeName` — what changes and why
- `function_name()` return type — what it currently returns vs. what it should
- Config shape — any new options needed

**Acceptance criteria:**
- [ ] Concrete, testable criterion 1
- [ ] Concrete, testable criterion 2
- [ ] Concrete, testable criterion 3

**Verification:** (required for ready-for-agent; optional for ready-for-human)
A specific runnable command or check that returns success/failure without human judgment.
Examples:
- `pytest tests/skills/test_triage.py -k 'needs_info'`
- `curl -fsS https://localhost:8080/health | jq -e '.status == "ok"'`
- A screenshot diff against `assets/expected/feature.png`

**Repo policies in effect:**
Load-bearing constraints from `CLAUDE.md` / `docs/agents/` that apply here:
- (e.g.) No new third-party dependencies without an ADR
- (e.g.) Ask before schema migrations on the `orders` table
- (e.g.) Secrets only via environment variables, never committed

**Out of scope:** (omit if nothing slice-specific)
- Things that should NOT be changed or addressed in this issue
- Adjacent feature that might seem related but is separate
```

## Worked examples

### Example 1 — bug, ready-for-agent

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** PRD titles longer than 60 chars are truncated in the issue list.

**Current behavior:**
When a PRD issue's title exceeds 60 characters, the listing view truncates without an ellipsis, making it ambiguous which issue is which.

**Desired behavior:**
Titles are displayed in full when space allows, or truncated with a trailing `…` when they don't fit.

**Key interfaces:**
- The `IssueListItem` rendering helper that decides display width
- No new public types

**Acceptance criteria:**
- [ ] Titles ≤60 chars render as-is
- [ ] Titles >60 chars truncate at the last word boundary before 60 chars and append `…`
- [ ] All call sites of `IssueListItem` get the new behavior automatically

**Verification:**
`pytest tests/ui/test_issue_list.py -k 'truncation'` passes.

**Repo policies in effect:**
- No new third-party dependencies — use the project's existing string utilities.
```

### Example 2 — enhancement, ready-for-human

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Add a `--dry-run` flag to the deploy command.

**Current behavior:**
`deploy` runs the full pipeline immediately. There is no way to preview what would change without committing.

**Desired behavior:**
`deploy --dry-run` prints the plan (resources to create/update/delete, env-var diff, predicted blast radius) and exits 0 without touching any infra.

**Key interfaces:**
- The `Deployer.run()` method gains a `dry_run: bool = False` parameter
- A new `Deployer.plan()` method returns a structured plan without side effects

**Acceptance criteria:**
- [ ] `deploy --dry-run` prints a plan and makes no API calls to AWS
- [ ] The plan output format is human-readable and machine-parseable (JSON via `--format=json`)
- [ ] Existing `deploy` (no flag) behavior is unchanged

**Why this needs a human:**
The plan format is a public-ish surface — downstream automation will start parsing it. Need design review on the JSON schema before implementation.

**Repo policies in effect:**
- Public output format changes require an ADR.
```

## What a *bad* Agent Brief looks like

```markdown
PRD says we need to handle long titles. Fix it.
```

No category. No acceptance criteria. No verification. No specific interfaces. The agent will guess, and the guesses will be wrong.
