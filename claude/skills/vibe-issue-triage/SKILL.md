# vibe-issue-triage

Moves issues through a 5-state × 2-category state machine. Produces durable artifacts on terminal states: an **Agent Brief** comment when an issue moves to `ready-for-agent` (or `ready-for-human`), an entry in `.out-of-scope/` when an enhancement moves to `wontfix`.

## State machine

**Two category roles** (1 per issue, orthogonal to states):

- `bug` — something is broken
- `enhancement` — new feature or improvement

**Five state roles** (1 per issue):

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on reporter for more information
- `ready-for-agent` — fully specified, an AFK agent can pick it up
- `ready-for-human` — needs human implementation (architectural call, design review, judgment)
- `wontfix` — will not be actioned

**Transitions:**

```
unlabeled → needs-triage → { needs-info, ready-for-agent, ready-for-human, wontfix }
                ▲
                │
needs-info ─ reporter replies ─┘
```

The canonical role names map to actual repo label strings via `docs/agents/triage-labels.md`. If that mapping doesn't exist, proceed with the canonical role names as defaults.

## Mandatory AI disclaimer

**Every** comment this skill posts starts with this prefix on its own line:

```
> *This was generated by AI during triage.*
```

No exceptions. Maintainers and reporters need to know which comments came from the skill versus a human.

## Two flows

### Flow A — "Show me what needs my attention"

Query the issue tracker and present three buckets, **oldest first**:

1. **Unlabeled** — never triaged
2. **`needs-triage`** — evaluation in progress
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation

For each bucket: show the count and a one-line summary per issue (number, title, age). Wait for the maintainer to pick which issue to triage next.

### Flow B — "Triage #42" (per-issue)

Five steps. **Don't skip the recommend-and-wait step** — the maintainer sees the recommendation before any labels or comments are applied.

#### 1. Gather context

- Read the issue body, all comments, labels, reporter, dates
- Parse any prior triage notes (look for the AI-disclaimer prefix on past comments) — **don't re-ask resolved questions**
- Explore the codebase using the project's domain glossary; respect existing ADRs
- Read `.out-of-scope/*.md` and surface any prior rejection that resembles this issue (match by concept similarity, not keyword)

#### 2. Recommend + wait

Tell the maintainer your proposed category and state with reasoning, plus a brief codebase summary. **Wait for direction before applying any labels.** This is the approval gate.

#### 3. Reproduce (bugs only)

Before grilling, attempt reproduction. Read the reporter's steps, trace the relevant code, run tests/commands. Report exactly one of three outcomes:

- **Successful repro** — describe what you saw; this makes a much stronger Agent Brief downstream
- **Failed repro** — describe what you tried and what happened instead; some bug reports are genuinely broken on the reporter's end
- **Insufficient detail** — strong `needs-info` signal; describe what's missing

#### 4. Grill (if needed)

If the issue needs fleshing out before it can be acted on, run `/vibe-grill` to drive a Socratic interview against the project's domain model. Skip if the issue is already concrete.

#### 5. Apply outcome

Branch on the chosen state. **Apply both** the category label (`bug` or `enhancement`) and the state label using the strings from `docs/agents/triage-labels.md`.

- **`ready-for-agent`** — post an **Agent Brief** comment using [references/AGENT-BRIEF.md](references/AGENT-BRIEF.md). The brief is the contract the AFK agent will work from; treat the original issue as context.
- **`ready-for-human`** — post a brief in the same shape, but include a short note explaining why it can't be delegated (judgment, external access, design call, manual testing).
- **`needs-info`** — post a Triage Notes comment listing the specific questions to be answered. Apply the `needs-info` label.
- **`wontfix`** + bug — post a polite explanation and close. No `.out-of-scope/` entry — out-of-scope is for *concepts*, and a closed bug is just "we don't think this is broken."
- **`wontfix`** + enhancement — write or append to `.out-of-scope/<concept>.md` (see [references/OUT-OF-SCOPE.md](references/OUT-OF-SCOPE.md)). Post a comment explaining the decision and linking the file. Then close.
- **`needs-triage`** (partial progress) — apply the label, optionally post a comment summarizing what's been figured out so far.

## Quick override

If the maintainer says "move #42 to ready-for-agent" or similar, **trust them**. Confirm what you're about to do (which labels you'll change, what comment you'll post if any, whether you'll close). Then act. Skip the grilling step.

If moving to `ready-for-agent` *without* a prior grill session, ask whether to write an Agent Brief — the issue body alone may not be enough.

## Resuming a previous session

If prior triage notes exist on an issue (look for the AI-disclaimer prefix on earlier comments):

1. Read them all, in order
2. Check whether the reporter has replied to any outstanding questions since the last note
3. Present an updated picture before continuing — what was asked, what was answered, what's still open

**Don't re-ask resolved questions.** The whole point of recording the notes is so the next pass picks up where the last left off.
